// HADA AIコーディングエージェント運用・保守ルール Ver.1.0.0.20260908

目的: エージェント依存削減,Cursor/Codex/Claude Code等の相互運用性確保,プロジェクト知識の永続化,作業履歴の再利用,安全な自動化,保守性向上,監査性向上

基本: AIエージェントは実行主体として扱い,特定エージェントを前提としない,プロジェクト固有の基本方針はAGENTS.mdを正規情報源とする,AI/をエージェント非依存の作業領域とする,.cursor/等のエージェント固有領域はアダプター用途に限定する,エージェント変更時もプロジェクト知識と作業履歴を継続利用できる構造とする

AGENTS.md: プロジェクト目的,対象範囲,アーキテクチャ,ディレクトリ構成,実装規約,安全規約,作業手順,Git規約,テスト規約,報告規約,停止条件,承認条件を定義する,エージェント固有機能を前提としない,他のエージェントでも解釈可能な記述を優先する

AI/: エージェント非依存の作業情報を保存する,ユーザー指示,エージェント回答,タスク,計画,分析,実装結果,テスト結果,判断事項,修正履歴,状態,必要なログ,作業履歴を保存対象とする,Cursor/等のエージェント名をフォルダ名として使用しない,将来のエージェント移行時に再利用可能な形式を優先する

AI/tasks/: タスク定義,作業目的,対象範囲,制約,完了条件を保存する,小さな作業は小さなタスクとして管理する,無関係な作業を同一タスクへ統合しない

AI/reports/: 分析結果,実装結果,テスト結果,セキュリティ確認,差分確認,リリース確認等を保存する,報告は監査可能な要約を基本とし,巨大な実行ログを通常報告へ含めない

AI/history/: ユーザー指示とエージェント応答の履歴を可能な範囲で保存する,将来のエージェント移行や判断根拠の再確認に利用できる形を維持する,巨大な生ログは必要性がある場合のみ保存する

AI/state/: 現在の作業状態,未完了事項,承認状態,次のアクション等を保存する,現在状態と過去履歴を混在させない

AI/logs/: 必要な場合のみ詳細ログを保存する,通常の報告へ大量ログを転記しない,再現性,障害調査,監査等に必要なログを優先して保存する

エージェント固有領域: .cursor/,Claude Code固有設定,Codex固有設定等は共通情報の保存場所としない,共通ルールをエージェント固有設定へ重複保存しない,エージェント固有機能が必要な場合のみアダプターとして使用する

プロンプト: 目的,対象範囲,制約,禁止事項,停止条件,完了条件,検証方法,報告形式を明示する,暗黙の前提を可能な限り減らす,複数の独立した作業を過度に一つのプロンプトへ統合しない,小規模変更では小規模プロンプトを使用する

作業範囲: 指定されたファイル,ディレクトリ,リポジトリのみを対象とする,対象外の変更を行わない,関連性だけを理由として変更範囲を拡大しない,不明点は確認する,拡大解釈しない,勝手に書き換えない

変更: 必要最小限の変更とする,Small Intentional Diffを原則とする,無関係なリファクタリング禁止,不要な整形禁止,不要な空白変更禁止,不要な改行変更禁止,行末変更禁止,依頼されていないファイル変更禁止,依頼されていない依存関係変更禁止,依頼されていない構成変更禁止

変更前状態: 作業開始前に存在した変更はユーザーまたは他の作業によるものとして扱う,その所有者や意図を推測して変更,整理,破棄しない,作業前後の状態を比較する,エージェント自身が行った変更を識別可能な状態にする

判断: 通常の実装,調査,テスト等はエージェントが実行できる,要件変更,仕様変更,対象範囲拡大,公開,リリース,本番変更,不可逆操作,セキュリティ上重要な操作は人間の承認対象とする,判断根拠が不明な場合は推測せず確認する

事実: 事実,確認済み情報,推測,提案を区別する,確認していない情報を確認済みとして扱わない,推測に基づく変更を行わない

停止: 不明な要件,曖昧な仕様,対象範囲外の変更が必要,予期しない依存関係,想定外の大量差分,セキュリティリスク,認証情報へのアクセス,外部リポジトリへの意図しないアクセス,本番環境への変更,不可逆操作が必要な場合は停止して報告する

Git: Git状態を作業前後に確認する,既存のユーザー変更を勝手に破棄しない,無関係な変更をコミット対象へ含めない,差分を確認する,大きな差分や想定外の差分が発生した場合は停止する,commitは明示的に許可された場合のみ実行する,pushは原則として人間が実行する,reset,rebase,force push等の破壊的操作は人間の明示的承認なしに実行しない

外部アクセス: 指定されたリポジトリ,サービス,アカウントのみ使用する,無関係なGitHub Organization,Repository,Cloud Service等へアクセスしない,認証情報,APIキー,トークン,パスワードを取得,保存,出力しない,公開リポジトリへ個人情報,秘密情報,内部情報を含めない

権限: AIエージェントにはタスク遂行に必要な最小限の権限,アクセス範囲のみを与える,不要な認証情報,アカウント,サービス,リポジトリ,環境へアクセスしない

ワークフロー: Task → Validate → Analyze → Plan → Approval? → Implement → Test → Scope Check → Security Check → Diff Review → Release Candidate → Human Approval → Release

検証: 変更ファイルを確認する,テストを実行する,必要なValidatorを実行する,Git diffを確認する,スコープ違反を確認する,セキュリティ上の問題を確認する,公開対象の場合は公開安全性を確認する,失敗した検証結果を成功として報告しない

完了: 一部のテストや検証に成功しても完了条件を満たしていない場合はタスク全体を完了として扱わない,未完了事項,失敗した検証,既知の問題を明示する

報告: ステータス,変更ファイル,変更ファイル数,テスト結果,検証結果,Git状態,問題,次のアクションを簡潔に報告する,ファイル名を明示する,テスト件数を可能な限り数値で示す,commitした場合はcommit IDを示す,pushした場合はその事実を示す,pushしていない場合も明示する,詳細ログは必要時のみ提示する

報告形式: [STATUS],[CHANGED],[TEST],[VALIDATION],[GIT],[ISSUES],[NEXT]を基本形式とする,READY/NEEDS_FIX/BLOCKED等の状態を明示する,問題は重要度の高いものを優先し通常最大3件程度に圧縮する,次のアクションを必ず明示する

履歴: ユーザー指示とエージェント回答はプロジェクト資産として扱う,重要な判断,仕様変更,承認,修正理由,検証結果を保存する,将来のエージェントが過去の判断を再利用できる状態を維持する,履歴保存のために不要な巨大ログを常時蓄積しない

知識: 恒久的なプロジェクト知識はAGENTS.md,docs/,config/等の適切な正規場所へ保存する,一時的なタスク情報を恒久的知識へ混在させない,エージェントの会話履歴だけを唯一の知識源にしない,再構築可能な情報は再生成可能な形で管理する

生成物: AIが生成した一時的な作業成果物と,プロジェクトとして保存すべき判断,知識を区別する,一時生成物を恒久的なプロジェクト知識として保存しない

機械可読性: 人間が読めるMarkdownを基本とし,状態,設定,構成,結果等の機械処理が必要な情報にはYAML/JSON等を使用する,特定エージェント専用形式への依存を可能な限り避ける

ライブラリ: 既存の適切なライブラリで実現できる機能は既存ライブラリを使用する,独自実装を優先しない,新規依存関係が必要な場合は理由と影響を明示する

自動化: 決定的処理はコードで実行し,意味判断,要約,翻訳,分類等の非決定的処理はAIを利用する,AIに判断させる必要のない処理をAIへ過度に委譲しない,自動化レベルを明示し,人間承認が必要な工程を省略しない

将来機能: 未依頼の機能を実装しない,将来構想を現在の実装へ混入させない,将来拡張可能な設計と未実装機能を明確に区別する

公開: 公開リポジトリには公開可能な情報のみを含める,個人情報,認証情報,秘密情報,顧客情報,ローカル絶対パス,内部ログ,内部判断,非公開リポジトリ情報を含めない,公開前にセキュリティと構成を確認する

再利用: 他プロジェクトへコピー可能なポリシーとプロジェクト固有情報を分離する,プロジェクト固有名,パス,サービス,依存関係を共通ポリシーへ不用意に埋め込まない,AGENTS.mdとAI/を移植可能な構造として維持する

互換性: Cursor,Codex,Claude Code等のエージェント間で同一のプロジェクトルール,作業履歴,判断記録,検証結果を利用できることを優先する,特定エージェントでしか理解できない記法を共通仕様にしない

保守: 共通ポリシーを変更する場合はAGENTS.mdとの整合性を確認する,エージェント固有設定を変更する場合は共通ポリシーへの影響を確認する,同一ルールの重複定義を増やさない,ルール間で矛盾が発生した場合は共通仕様を優先し要確認として扱う

禁止: エージェント依存の作業履歴保存,無断での対象範囲拡大,無断での本番変更,無関係なファイル変更,巨大な不要ログの常時保存,秘密情報の保存,外部リポジトリへの無断アクセス,未依頼機能の実装,要件の推測による変更,失敗結果の隠蔽,ユーザー承認の省略,既存変更の無断破棄,確認していない情報の事実としての扱い

出力: 完了条件未達時の完了報告禁止,失敗した検証結果の成功報告禁止,推測と確認済み情報の混同禁止,重要な未完了事項の省略禁止

# 2. 検証で確認されたこと

* **① 詳細なターゲットプロンプトを先に作ることが重要** — 生成に必要な具体的情報を最初から保持できる。
* **② 後からプロンプト保守ルールを適用しても情報をほぼ維持できる** — 構造整理と重複排除が中心になるため安全性が高い。
* **③ 最初からプロンプト保守ルールを適用すると情報欠落が起こり得る** — AIが「保守・圧縮」を「要約」と誤解する可能性がある。
* **④ 上位概念への置換が最大の危険** — 具体的な部位・形状・位置などを抽象化すると、ターゲットプロンプトの生成制御能力が低下する。
* **⑤ 文字数の圧縮と情報の圧縮は別物** — 改行・空白・完全重複の削減は安全だが、具体情報の削除は危険。
* **⑥ 通常生成後ルール適用版は非常に効率が良い** — 元の詳細さを保ちながら、管理しやすい形式へ整理できる。
* **⑦ 文字数削減効果そのものは小さい** — 今回は通常生成版→通常生成後ルール適用版で約1.8%程度の削減だった。
* **⑧ 6K文字前後から長文出力のリスクを意識する価値がある** — 長文化すると圧縮時に情報欠落が起きやすくなる。
* **⑨ 10K文字を超える領域ではさらに破綻リスクが高まる** — 長大なターゲットプロンプトを無理に一括保守しない方が安全。
* **⑩ 最適なのは「生成→保守→改良」の分離運用** — 新規作成と保守を同じコンテキストに最初から混在させない。

# 3. 推奨使用法

**新規ターゲットプロンプトは、新規スレッドでプロンプト保守ルールを適用せず通常生成する。**

完成したターゲットプロンプトを確認した後、**プロンプト保守ルールをスレッドに読み込ませ、既存プロンプトへ適用する。**

以後は、

**通常生成 → プロンプト保守ルール適用 → 改良 → 保守**

の順で運用する。

### メリット

* 初期生成時の情報量・創造性を最大化
* 保守時の情報欠落を最小化
* 重複・不要な改行・構造を整理できる
* プロンプトを簡潔かつ管理しやすく維持できる
* ルール適用による「要約化・抽象化」の事故を避けやすい
* 長文化した場合も、**6K〜8K文字程度を一つの実用上の目安**として管理できる
* 10K文字級まで無理に膨らませず、必要なら分割・整理を検討する
